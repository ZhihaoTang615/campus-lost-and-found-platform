# Known Limitations

These are confirmed boundaries of the delivered Flask/MySQL university
project. The user system and read-only administrator view are implemented;
remaining workflow and production-hardening items are not presented as defects
in the delivered viewing scope.

| Limitation | Current impact | Current mitigation | Possible future improvement |
|---|---|---|---|
| Pre-enhancement legacy rows have no account owner | Rows created before the account migration may have `user_id = NULL` and therefore cannot appear in any account's My Reports list. Current routes require login and do not create new unowned rows. | Nullable ownership preserves every baseline record; the Admin Dashboard shows old null-owner rows through `LEFT JOIN` with the legacy fallback labels. | Add a separately authorized, audited ownership-assignment process if a confirmed requirement is provided. |
| Admin Dashboard is read-only | Administrators can view item and claim records but cannot approve, reject, delete, ban, or update anything. | The narrow implementation matches the lecturer-requested viewing scope and exposes no write controls or POST route. | Design US09 with explicit decisions, audit history, and authorization before adding review actions. |
| No claim history or tracking page | A claimant cannot later view their submitted claims or follow status changes. | The submission confirmation shows the initial Pending status. | Implement US08 with an authenticated claim-history and status model. |
| No item-status update workflow | Users and administrators cannot change an item from active to claimed or returned. | Existing status values remain visible and stable. | Implement US10 with ownership/administrator rules and audit history. |
| My Reports is view-only | The delivered US11 slice lists owned item reports but does not edit, delete, or otherwise manage them. | It strictly filters by the signed-in account ID and links to authenticated details. | Add separately authorized edit/manage requirements after defining ownership and history rules. |
| Limited account lifecycle | There is no email verification, password reset, password change, profile edit, account deletion, or self-service administrator registration. | Public registration always creates `user`; administrators are created locally with the secure script. | Add verified email delivery and token-based recovery only if deployment requirements justify them. |
| Session role is refreshed only at login | A role change made directly in MySQL is not reflected in an already signed-in session until that session is cleared and the user logs in again. | Login normalizes the stored role and authorization checks the signed session on every protected request. | Re-read authorization state from the database or introduce session invalidation for a larger system. |
| Security hardening is incomplete | The project has no CSRF tokens, login throttling, lockout, multi-factor authentication, penetration test, or comprehensive abuse controls; `Secure` cookies require a reviewed HTTPS deployment setting. | Password hashing, required environment secret, HTTP-only/SameSite cookies, parameterized SQL, safe local redirects, POST-only logout, trusted session authorization, and Jinja escaping cover the confirmed course scope. | Add CSRF protection, rate limiting, HTTPS-only cookie settings, threat modeling, logging policy, and security testing before public deployment. |
| Automated database tests use fakes or mocks | The **95-pass** suite does not prove MySQL connectivity, fresh-schema import, or migration execution. | SQL shape, parameters, commits, ownership filtering, authorization, and resource cleanup are checked deterministically without a shared database. | Add disposable-MySQL integration tests and a tested migration pipeline. |
| No automated browser or accessibility suite | Cross-page browser behavior, responsive layout, and accessibility are not continuously verified. | Flask test-client coverage and historical screenshots exercise representative paths. | Add browser end-to-end, accessibility, and cross-device checks. |
| No recorded coverage percentage | The percentage of executable code covered by tests is unknown. | Traceability identifies the exact behaviors asserted by the baseline and refinement tests. | Add a coverage tool and agreed threshold. |
| No pagination or load testing | Large item/claim tables may make Browse, My Reports, and Admin Dashboard pages slow or unwieldy. | The delivered use case is a small local course project with newest-first ordering. | Add pagination, indexes based on measured queries, performance targets, and load tests. |
| Upload validation remains limited | Extension checks and filename sanitization do not enforce MIME type, size, uniqueness, malware scanning, or orphan cleanup. | Accepted extensions are limited and runtime uploads are ignored by Git. | Add content validation, size limits, collision-safe names, managed storage, and scanning. |
| Item Details exposes reporter contact information to authenticated users | Any signed-in account that can browse an item can see the contact value stored with that report. | Login limits the record pages to authenticated accounts; private claim details are limited to the administrator view. | Confirm a privacy policy and replace direct contact details with mediated messaging if required. |
| Local deployment only | No public production deployment of the Flask/MySQL application is evidenced. | Reproducible local setup, environment placeholders, migration instructions, and a required secret are documented. | Add reviewed WSGI hosting, HTTPS, secret management, backups, monitoring, and recovery procedures. |

Historical Iteration 3 files still record the earlier deferral of US08-US11.
The later lecturer-requested refinement delivers the view-only My Reports slice
without changing those historical records. It does not deliver US08, US09,
US10, or a broader report-management workflow.
